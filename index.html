Troubleshooting 01

신뢰도 보정과 재검사율 개선

등급 예측이 맞아도 신뢰도가 기준에 못 미쳐 재검사로 분류되는 경우가 많아, 개발 데이터 152개 사과의 교차검증 결과를 살펴봤다. 재검사율은 23.7%였으며, 품질 예측 확률과 실제 정답률 사이의 보정 오차(ECE)가 0.259로 나타나 모델의 신뢰도를 보정할 필요가 있었다.

이를 개선하기 위해 개발 교차검증 예측에 온도 보정을 적용하고, 자동 선별 기준도 품종 0.50·품질 0.60으로 조정했다. 예측 라벨과 모델 가중치를 유지하면서 확률을 보정하는 방식이라, 재학습 없이 설정 파일만 바꿔 추론 서비스에 반영할 수 있었다.

같은 개발 자료로 다시 확인한 결과, 재검사율이 23.7% → 16.4%로 줄고 품질 보정 오차도 0.259 → 0.081로 낮아졌다. 자동 처리 구간의 품질 정확도 역시 92.2% → 92.9%로 유지돼, 정확도를 떨어뜨리지 않으면서 재검사를 줄일 수 있었다. 이 수치는 개발 교차검증 결과로 기록했으며, 새로운 사과에 대한 최종 검증은 별도로 남겨두었다.

Troubleshooting 02

GitHub 이슈 기반 협업

4명이 데이터·모델, 화면, Backend, 배포를 나눠 맡고 각자 AI 에이전트와 작업하면서, 파트 간 요청과 결과는 디스코드로 공유했다. 그런데 메시지가 쌓일수록 누가 무엇을 맡았고 어디까지 끝냈는지 파악하기 어려워졌고, 필수 기능인 ‘처리 중 사과 표시’가 누락된 것도 서버 화면을 확인한 뒤에야 알게 됐다.

요청과 진행 상황을 한곳에서 확인할 수 있도록 이슈 #39에 [담당][WBS] 제목 규칙, 파트·종류·우선순위 라벨과 요청·버그·결과·결정 양식을 정리했다. 이를 바탕으로 사람과 에이전트가 같은 이슈에서 요청 → 계획 댓글 → 담당자 확인 → 결과·PR → 병합·종료를 따라가도록 했으며, 결과 댓글에는 측정값과 다른 파트에 미치는 영향도 함께 남겼다.

실제로 이슈 #53에서는 화면 담당이 미리보기 이미지의 용량과 만료 응답을 측정한 뒤, Backend에 축소본 제공과 표시 유예를 요청했다. 이후 Backend의 최근 완료 사과 응답에 FE의 1초 조회·마지막 사과 유지 기능을 연결해, 배포 화면에서 14초 동안 들어온 사과 7개가 모두 표시되는 것을 확인했다. 요청과 수정 내용부터 서버 검증, 사용자 확인 후 종료까지 같은 이슈에 기록하면서, 다른 파트의 변경 사항과 해결 근거를 매번 다시 전달하던 부담도 줄일 수 있었다.

Troubleshooting 01

제한된 데이터로 실시간 시연 구현

첫 프로젝트에서는 데이터셋 탐색보다 문제 정의를 먼저 진행해 적절한 데이터를 찾는 데 어려움이 있었고, 결국 전처리가 잘되어 있고 문제에도 적합하지만 규모가 작은 데이터셋을 사용하게 됐다. 그래서 원본 센서 데이터는 상태 예측 모델 학습에 모두 활용하고, 실시간 시연에 필요한 데이터는 별도의 시계열 생성 LSTM 모델로 만들어 공급했다.

LSTM이 학습한 17개 센서의 시간 흐름을 바탕으로 가상 데이터를 계속 생성하도록 구성해, 세 설비에서 실시간으로 데이터가 들어오는 상황을 재현했다. 덕분에 작은 데이터셋으로도 예측 결과가 대시보드와 디지털 트윈에 반영되는 전체 흐름을 시연할 수 있었다.

Troubleshooting 02

AI 에이전트 작업 후 개발환경 정리

협업 중 AI 에이전트가 용도가 불분명한 디렉터리와 파일을 반복해서 추가하면서, 실제 개발환경이 미리 정한 Git · Jenkins · MLOps 구조와 어긋나기 시작했다. 문서와 실제 구성을 비교해 차이가 생긴 지점을 담당 팀원에게 설명하고, 함께 개발환경을 다시 정리했다.

같은 문제가 반복되지 않도록 에이전트에게 기획과 작업 목적을 먼저 전달하고, 생성된 코드와 환경 변경은 사람이 확인한 뒤 반영하는 원칙을 팀원들과 공유했다. 이 과정에서 AI를 활용할 때도 작업 범위와 검토 기준이 명확해야 협업 속도를 유지할 수 있다는 점을 배웠다.

Troubleshooting

특정 기기 오류 재현 및 해결

별점이 떨어지고 오류 리뷰가 올라왔지만, QA와 사내 테스트에서는 같은 문제가 재현되지 않아 원인을 파악하기 어려웠다. 그래서 문제가 발생한 사용자들에게 연락해도 되는지 먼저 양해를 구하고, 기기와 사용 환경 정보를 모아 공통점을 찾아보기로 했다.

확인된 사용자 대부분이 어르신이라는 점에서 오래된 기기나 효도폰과 관련된 문제를 의심했고, 기종 정보를 추가로 수집하면서 오류가 특정 모델에 집중돼 있다는 것을 알게 됐다. 같은 Android 버전이어도 기기에 따라 One UI 버전이 달랐기 때문에, Android 버전뿐 아니라 기기별 환경까지 확인할 필요가 있었다.

해당 기종을 중고로 직접 구한 뒤 오류를 재현할 수 있었고, 같은 환경에서 수정안을 검증해 문제를 해결했다. 사내에서 재현되지 않는 오류도 사용자와 기기의 공통점을 살펴보면 원인을 좁혀갈 수 있다는 점을 경험한 사례였다.
