Troubleshooting 01

맞힌 사과도 재검사로 보내던 신뢰도 문제

모델이 정답을 맞혀도 신뢰도가 낮아 재검사로 보내는 경우가 많았다. 개발 데이터 152개 사과의 교차검증 예측을 확인하니 재검사율은 23.7%였고, 품질 예측 확률과 실제 정답률 사이의 보정 오차(ECE)는 0.259였다.

모델을 다시 학습하기 전에 확률이 실제 정답률을 반영하는지부터 점검했다. 개발 교차검증 예측에 온도 보정을 적용하고, 자동 선별 기준을 품종 0.50·품질 0.60으로 다시 정했다. 예측 라벨과 모델 가중치는 유지한 채 설정 파일만 바꿔 추론 서비스에 반영했다.

같은 개발 자료에서 재검사율은 23.7% → 16.4%, 품질 보정 오차는 0.259 → 0.081로 줄었다. 자동 처리 구간의 품질 정확도도 92.2% → 92.9%로 유지됐다. 결과는 개발 교차검증 기준으로 기록하고, 새로운 사과에 대한 최종 검증은 별도로 남겼다.

Troubleshooting 02

흘러가던 파트 간 요청을 GitHub 이슈로 연결하기

4명이 데이터·모델, 화면, Backend, 배포를 나눠 맡고 각자 AI 에이전트와 작업했다. 디스코드로 요청과 결과를 공유하다 보니 담당자와 완료 여부를 다시 찾기 어려웠고, 필수 기능인 ‘처리 중 사과 표시’도 담당 이슈 없이 남아 서버 화면에서야 누락을 발견했다.

이슈 #39에 제목 [담당][WBS], 파트·종류·우선순위 라벨과 요청·버그·결과·결정 양식을 정리했다. 사람과 에이전트가 같은 이슈에서 요청 → 계획 댓글 → 담당자 확인 → 결과·PR → 병합·종료를 추적하도록 하고, 결과 댓글에는 측정값과 다른 파트에 미치는 영향까지 남겼다.

실제 협업 사례인 이슈 #53에서는 화면 담당이 미리보기 이미지의 용량과 만료 응답을 측정해 Backend에 축소본·표시 유예를 요청했다. Backend의 최근 완료 사과 응답과 FE의 1초 조회·마지막 사과 유지 기능을 맞춘 뒤, 배포 화면에서 14초 동안 들어온 사과 7개가 모두 표시되는 것을 확인했다. 요청부터 수정·서버 확인·사용자 확인 후 종료까지 한 이슈에 남아, 다른 파트의 변경과 해결 근거를 대화마다 다시 전달할 필요가 줄었다.

Troubleshooting 01

작은 데이터셋으로 실시간 시연까지 연결하기

강의실 컴퓨터 사양으로는 대형 데이터셋을 학습하기 어려웠다. 사용할 수 있는 유압 센서 데이터는 상태 예측 모델 학습에 모두 활용하고, 별도의 시계열 생성 LSTM 모델을 추가하는 방향을 택했다.

LSTM이 17개 센서의 시간 흐름을 학습해 가상의 실시간 데이터를 만들도록 구성했다. 덕분에 제한된 학습 환경에서도 세 설비의 데이터가 계속 유입되고, 예측부터 대시보드와 디지털 트윈까지 이어지는 전체 흐름을 시연할 수 있었다.

Troubleshooting 02

AI 에이전트로 흐트러진 개발환경 복구하기

협업 과정에서 목적이 분명하지 않은 디렉터리와 파일이 반복해서 추가되면서, 미리 정한 Git · Jenkins · MLOps 구조와 실제 환경이 어긋나는 일이 생겼다. 문제가 생긴 지점을 문서와 비교해 하나씩 설명하고, 담당 팀원과 함께 개발환경을 다시 정리했다.

이후에는 에이전트에게 기획과 작업 목적을 먼저 명확히 전달하고, 생성된 코드와 환경 변경을 반드시 사람이 확인한 뒤 반영하는 원칙을 공유했다. AI를 빠르게 쓰는 것보다 결과를 검증할 수 있는 작업 기준을 세우는 일이 먼저라는 점을 배웠다.

Troubleshooting

사내에서는 재현되지 않던 특정 기종 오류 찾기

별점이 떨어지고 오류 리뷰가 올라왔지만, QA와 사내 테스트에서는 같은 문제가 전혀 발생하지 않았다. 막연히 사용자 실수로 판단하지 않고, 문제가 발생한 사용자들에게 연락해도 되는지 먼저 양해를 구한 뒤 사용 환경 정보를 모았다.

확인된 사용자 대부분이 어르신이라는 공통점에서 오래된 기기나 효도폰 문제일 수 있다는 가설을 세웠다. 기종 정보를 추가로 수집하자 오류가 특정 모델에 집중되어 있었고, 같은 Android 버전이어도 기기에 따라 One UI 버전이 다를 수 있다는 사실을 확인했다.

해당 기종을 중고로 직접 구해 마침내 오류를 재현했고, 그 환경을 기준으로 수정안을 검증해 해결했다. 재현이 안 되는 문제일수록 리뷰 문장만 보는 대신 사용자 특성에서 가설을 세우고, 기기와 OS 환경을 단계적으로 좁혀야 한다는 점이 가장 기억에 남았다.
